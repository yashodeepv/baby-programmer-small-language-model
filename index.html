01System

Two systems. A verified program generator and a small transformer. The generator is the substantial half — the model is largely an instrument for measuring what the generator managed to teach.

The property everything rests on

lower() and evaluate() are independent implementations of the same semantics — one emits machine code, the other interprets in Python. Neither derives from the other, so a codegen bug surfaces as an execution mismatch. A verifier that ran the same code twice would prove nothing.

02The IR

IR — intermediate representation: a description of what a program means, held as a data structure rather than text. The same idea a compiler uses; clang parses C into an IR, optimises it, then emits machine code. This one has about a dozen node types where LLVM has hundreds.

The unit of training data is one object:

Loop(op='sum', lo=Const(2), hi=Const(20), pred=('even', 0), mapf=None, k=0)

Written as three hand-maintained strings they would eventually drift, and across 20,000 programs some would be silently mislabelled. Derived from one object, the question cannot describe something the code does not do.

03Grammar

Mostly one form — reduce(op, map(f, filter(pred, source))) — with each axis chosen independently. That independence is the point: every axis is a word in the question that changes the code, so the qualifier must be read rather than ignored.

Two labels per program. shape_of encodes the whole subtree; cell_of records only the axis choices. The distinction matters for held-out splits — 91% of shapes occur exactly once, and a cell seen once cannot be withheld. cell_of yields ~420 cells with enough examples each to both train on and hold out.

04Register allocation

Allocation threads an explicit next-free index. The invariant: a node lowered into dst with free index f may only touch w{f}..w9, and dst always sits below f — so evaluating the right operand can never clobber the left one already in dst.

Three earlier schemes, all wrong

Random registers made the choice unpredictable from the question — pure noise in the training target. One template scored 54.5% because the model learned the dominant "reuse the register" pattern and emitted ldr w1 twice, clobbering a value.

One fixed register removed the noise but made the store block so uniform that the model stopped tracking position, and array indexing collapsed to a single constant offset.

Depth-derived collided: lowering and(251, w1) into w1 allocated its right operand at the same depth, emitting mov w1,#251 / mov w1,w11 / and w1,w1,w1 and losing the left operand silently. Parity tests missed it — no original template ever nested an expression inside a comparison.

x10 / w11the array pointer and length, parked

05Verification

Why batch. On macOS the first execution of a freshly built binary pays a code-signing check of roughly 0.45s, serialised machine-wide — one process per program is unusably slow, and threads do not help. Batching took full-corpus verification from 323s for 600 programs to 34s for 20,000.

Why one byte each. _write is unbuffered, so if the binary is killed the bytes already received say exactly how many programs finished — the next is the one that hung. Without it, a single non-terminating program fails 59 innocent neighbours.

Detection is based on progress, not elapsed time

A fixed deadline cannot tell "hung" from "slow to start" when the OS is serialising code-signing checks across parallel workers. An early version used a 3-second timeout and entered a death spiral — healthy batches charged as hangs, retried, more fresh binaries, longer queue. Caught at round 205. The watchdog now waits 30s for the first byte, then requires a new byte every 5s.

Property testing

Each program is called with ~12 input vectors — edges first (empty array, single element, lo == hi, lo > hi, negatives, all-equal, sorted), then random. Correct means every vector matches.

Single-input scoring called a hardcoded ldr w0, [sp, #4] a working “find the largest element” — index 1 happened to hold the maximum.

It overstated accuracy by 8 points, and overstated it most on the shapes that were most broken.

06Golden set

Execution validates the code against the oracle. It cannot validate either against the question — if the IR's meaning is misunderstood, both inherit the mistake, agree perfectly, and verification goes green on a mislabelled example. This happened twice:

  • A nested expression rendered as "21 plus 95 times 42" — by ordinary precedence 21+(95×42), while the tree meant (21+95)×42.
  • An array loop with a filter rendered identically to one without, silently dropping the word that changed the code.

68 cases whose expected values and question text were worked out by hand and never derived from the generator. The only hand-checked part of the system, and it covers all three views.

07The surface language

Questions are not free English. They are generated by ir.show(), which has exactly one rendering per node type — so the corpus contains one wording per operation, and the model never saw a paraphrase of any of them.

It fails silently, which is the dangerous part

Ask for "Sum the array" instead of "the sum of the elements of the array" and there is no error and no refusal. The model matches the nearest familiar shape and emits confident, compiling assembly that computes a different operation. A user with no reference to check against would conclude the model is simply wrong, rather than that they stepped outside its vocabulary.

This is a corpus limitation, not a model one. Nothing in the architecture prevents paraphrase — the training data simply never contained a second way to say "the sum of". Giving show() several wordings per node, the treatment the wrapper already received, is a corpus regeneration and a retrain rather than a research problem, and is the single largest usability gap today.

08Tokenizer

Assembly has a genuinely finite vocabulary, so tokens are matched by regex, longest-first, with no BPE and no learned merges. 390 tokens, fully reversible — and unknown input raises rather than being silently dropped.

09Model

q, k, v = self.qkv(x).split(n_embd, dim=2)     one matmul → three (B,T,512)
q, k, v = [t.view(B,T,8,64).transpose(1,2) …]  (B, 8 heads, T, 64)
y = F.scaled_dot_product_attention(q, k, v, is_causal=True, scale=0.125)

attention(Q,K,V) = softmax( (Q·Kᵀ) × scale + causal_mask ) · V
  • scale = 1/√64 = 0.125 — head size, not model width. An earlier version used 1/√512, dividing logits by 22.6 instead of 8 and flattening every softmax.
  • is_causal masks everything above the diagonal, which makes next-token prediction a valid signal on all 384 positions at once.
  • fused QKV replaced 3 matmuls per head inside a Python loop — identical math (max logit difference 1.55e-05), step time 924ms → 360ms.
ComponentShareDetail
feed-forward65%8 × (512→2048→512), GELU
attention33%fused qkv + output projection
embeddings · head · norms2%nearly free — the vocabulary is 390, not 50,000

KV cache — 6.4× measured

Causal masking guarantees an earlier position's keys and values never change once computed. Without a cache, every step recomputes the whole prefix and discards it: generating 300 tokens after a 60-token prompt processes 62,850 token-positions instead of 360. The positions ratio is 175×; measured wall-clock is 2.56s → 0.40s, because at this size per-step dispatch overhead dominates the arithmetic the cache removes. Output is byte-identical either way.

Two details that matter

Decoding is greedy — argmax, not sampling. The same question always produces the same answer, so a score reflects what the model learned rather than a lucky draw.

Generation stops at ret, which is a single token. Without that the model rolls straight on into an invented next USER: turn, so the continuation is also cut there before being parsed.

deeper training datano effect on depth extrapolation

Asked for an expression one level deeper than training, it emits valid, compiling code that is systematically too short — a depth-3 program for a depth-4 question.

Move the ceiling from 3 to 4 and the failure moves to 5. It learned a maximum depth, not a recursion.

The decomposition experiment localised it precisely: given a scratchpad to write the steps out first, on deep problems the model produced a correct decomposition 0.0% of the time, and even the right number of steps only 24.7%. It cannot break down a deep problem, because breaking it down is itself the recursive act.

Untried and likely worthwhile: cosine LR decay with warmup — the observed 85 → 66 → 93 oscillation at flat loss is what a too-high late learning rate looks like; masking loss to the answer only, since about a third of each step is spent predicting prompts; rotary position embeddings, because learned absolute ones cannot extrapolate past block_size; and giving the question renderer several wordings per operation, the single largest usability gap today.
